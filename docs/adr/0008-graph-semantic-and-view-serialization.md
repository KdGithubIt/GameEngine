# ADR 0008: Graph Semantic and View Serialization

Status: Accepted
Date: 2026-06-05

## Context

Graph behavior and graph presentation change for different reasons.

Semantic graph data is reviewed, validated, versioned, and eventually compiled
or interpreted by a graph domain. Presentation data is used for human
readability and may be regenerated by layout tooling. Storing both in one file
would create noisy diffs and make graph validity depend on editor state.

The canonical persisted authoring format remains an open decision, but the
current specification uses JSON examples and requires deterministic
serialization.

## Decision

Semantic graph data and graph view data are serialized as separate documents.

The initial JSON file naming convention is:

```text
<name>.graph.json
<name>.graph.view.json
```

The semantic graph document contains only behaviorally meaningful authoring
data, including:

- Graph identity, kind, and semantic schema version.
- Nodes and node properties.
- Edges and port references.
- Semantic groups.
- Semantic annotations.

The graph view document contains only presentation data, including:

- Node positions.
- Group bounds.
- Collapsed and pinned state.
- Viewport state.
- Edge routing hints.
- Layout policy and layout constraints.

`GraphView` is optional. Deleting or omitting the graph view document must not
invalidate the semantic graph document.

Node creation must not require pixel coordinates. A node without a view entry
is valid. Future layout tooling may generate or update view entries without
changing semantic graph data.

Both documents use deterministic field and map ordering, stable formatting,
typed identifier deserialization, and explicit schema versions where migration
is required. Runtime ECS entities, runtime asset IDs, renderer resources, and
compiled graph artifacts must not be serialized into either document.

Phase 3-A implements deterministic serialization for the semantic graph
document only. `GraphView`, auto-layout, and graph view serialization are
deferred.

Implementation note: Phase 3-A semantic graph serialization includes only
semantic graph data. In-memory transaction identity and revision fields are not
persisted; deserializing a graph creates a new in-memory document instance.

## Consequences

- Semantic graph diffs are not polluted by node movement or viewport changes.
- Graph documents remain usable by non-visual tools.
- Presentation data can be regenerated or deleted without changing behavior.
- Future save pipelines must validate and serialize semantic and view documents
  independently.
- Cross-document atomic save behavior remains deferred with multi-document
  transactions.

## Alternatives Considered

### Store semantic and presentation data in one file

Rejected because presentation-only edits would create semantic file churn and
make graph validity depend on editor state.

### Require a graph view file for every graph

Rejected because graph editing must work without coordinates or visual tooling.

### Store only layout hints in the semantic graph

Rejected because layout hints and layout results are presentation concerns and
must not affect semantic validity.

## Compatibility and Migration

No persisted graph files exist yet, so no migration is required.

The `.graph.json` and `.graph.view.json` names are an initial JSON convention.
A future canonical format ADR may change file extensions while preserving the
semantic and presentation separation defined here.
